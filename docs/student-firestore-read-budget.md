# 生徒機能のFirestore読み取り予算

## 運用前提

- 生徒数: 3,000人
- 授業参加: 1人あたり週2回（週6,000回、月平均約26,070回）
- 通常目標: 1回400〜1,200 reads
- 計画上限: 1回1,800 reads
- 絶対上限: 1回5,200 reads

計画値は月約1,043万〜4,693万reads、標準値は月約2,607万readsとする。

## 新機能の実装規則

1. 生徒画面からFirestoreの全件取得を追加しない。
2. 新しい一覧は必ず件数上限、期間、学年またはユーザーIDで絞る。
3. 更新頻度の低い共通データはサーバーキャッシュを共有する。
4. 同じデータを複数コンポーネントから取得せず、既存リクエストを共有する。
5. リアルタイム監視は同一ドキュメントにつき画面全体で1本までとする。
6. 非表示のモーダルや未使用機能では取得・監視を開始しない。
7. `loadCourseRegistrationOptions` の `force: true` は登録変更直後の既存1箇所以外に追加しない。
8. 新規取得を追加する場合は、同数以上の既存取得削減または明示的な読み取り予算更新を必要とする。

`npm run check:student-read-budget` は現在の取得箇所数を基準線として、新しい直接取得や強制再取得を検出する。本番ビルドでも自動実行される。

この検査は生徒導線だけでなく、アプリ全体のクライアント取得、上限なしのコレクション取得、サーバー側Firestore取得も基準線として固定する。機能追加時に取得箇所を増やす場合は、既存取得の統合・集計クエリ化・共有キャッシュ化によって同数以上を削減する。

## セキュリティ監視と読み取り予算

攻撃の監視（`lib/server/security-events.ts`・`lib/server/security-monitor.ts`）は、この予算を守るように作っている。

- 出来事の記録（ログイン失敗・回数制限・ログインなしのAPI呼び出し・脆弱性探り・署名違いの通知）は `FieldValue.increment` の書き込みだけで、読み取りはしない。
- 集計を読むのは監視ジョブだけ。1回の実行で、日別の集計1〜3件、しきい値以上のIP・アカウント最大20件/日、監査ログ最大200件。
- 1日1回の実行では月に最大約7,000 reads（計画値の月1,043万〜4,693万readsに対して0.07%未満）。
- 5分ごとに切り替えたとき（`hours=1`）は、1回あたり日別集計1〜2件・IPとアカウント最大10件・監査ログ最大50件に絞る。ふだんは数件で月に数万reads、上限まで読んでも月に約54万reads（計画値の下限の約5%）。


## 専任の勤怠と読み取り予算

専任の勤怠（`/api/dedicated-attendance`・`/api/admin/dedicated-attendance`）は、生徒・保護者の画面からは呼ばれない。

- 本人の画面：本人の勤務記録・時間外の予定・実施報告・授業・講習の授業・交通費（いずれも `user_id` で絞る、各最大1,000件）と、その月の報告書1件・講習期間の設定1件。
- 承認者の画面：表示中の月の範囲（勤務記録・予定・報告・授業・交通費）と、承認待ち（`status == pending`）だけを読む。講習期間の手当の一覧は、その講習期間の範囲だけ。
- 専任は数十人のため、1回の表示はおおむね数百〜数千 reads。旧 `/api/admin/dedicated-claims` は削除した。
