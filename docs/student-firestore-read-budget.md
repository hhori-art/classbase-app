# 生徒機能のFirestore読み取り予算

## 運用前提

- 生徒数: 3,000人
- 授業参加: 1人あたり週2回（週6,000回、月平均約26,070回）
- 通常目標: 1回400〜1,200 reads
- 計画上限: 1回1,800 reads
- 絶対上限: 1回5,200 reads

計画値は月約1,043万〜4,693万reads、標準値は月約2,607万readsとする。

## 新機能の実装規則

1. 生徒画面からFirestoreの全件取得を追加しない。
2. 新しい一覧は必ず件数上限、期間、学年またはユーザーIDで絞る。
3. 更新頻度の低い共通データはサーバーキャッシュを共有する。
4. 同じデータを複数コンポーネントから取得せず、既存リクエストを共有する。
5. リアルタイム監視は同一ドキュメントにつき画面全体で1本までとする。
6. 非表示のモーダルや未使用機能では取得・監視を開始しない。
7. `loadCourseRegistrationOptions` の `force: true` は登録変更直後の既存1箇所以外に追加しない。
8. 新規取得を追加する場合は、同数以上の既存取得削減または明示的な読み取り予算更新を必要とする。

`npm run check:student-read-budget` は現在の取得箇所数を基準線として、新しい直接取得や強制再取得を検出する。本番ビルドでも自動実行される。

この検査は生徒導線だけでなく、アプリ全体のクライアント取得、上限なしのコレクション取得、サーバー側Firestore取得も基準線として固定する。機能追加時に取得箇所を増やす場合は、既存取得の統合・集計クエリ化・共有キャッシュ化によって同数以上を削減する。
