# Vercel Fluid Compute 無料枠運用

## 予算

Hobbyプランの月間上限を次の3項目で管理する。

- Active CPU: 4 CPU時間
- Provisioned Memory: 360 GB時間
- Function Invocations: 1,000,000回

無料枠を使い切る前に対応できるよう、運用上の警戒線は各上限の70%とする。

| 指標 | 警戒線 | 上限 |
| --- | ---: | ---: |
| Active CPU | 2.8 CPU時間 | 4 CPU時間 |
| Provisioned Memory | 252 GB時間 | 360 GB時間 |
| Function Invocations | 700,000回 | 1,000,000回 |

## 実装方針

- `vercel.json` と診断環境設定で Fluid Compute を明示的に有効化する。
- APIの最大実行時間を原則60秒に制限し、異常な長時間実行を止める。
- 静的ファイルはMiddlewareの対象外とし、CDNから直接配信する。
- オンライン校管理画面は、表示中のみ2分間隔で更新する。手動更新も利用できる。
- 通知は、表示中のみ5分間隔で更新する。非表示タブではポーリングしない。
- CPU負荷の高いPDF生成はブラウザ側で行う。画像・Excel処理をAPIへ追加する場合は、件数とファイルサイズに上限を設ける。
- βテスト利用ログは端末側で最大25件までまとめ、30秒間隔または画面離脱時に一括送信する。APIでは1回の認証とFirestoreバッチ書き込みで処理する。
- 本番のβテスト利用ログは既定で `summary` とし、画面表示・離脱・エラーだけを記録する。クリック・表示状態・性能の詳細計測が必要な期間だけ、Vercel環境変数 `NEXT_PUBLIC_BETA_ANALYTICS_LEVEL=detailed` を設定して再デプロイする。完全停止は `off` とする。

## 月次確認

Vercelの `Usage` で直近30日を確認し、警戒線を超えた場合は次の順序で対応する。

1. 呼び出し回数上位のFunctionを確認する。
2. クライアントのポーリング、重複リクエスト、Botアクセスを止める。
3. CPU時間上位のFunctionで、全件走査、同期変換、巨大JSONの生成を見直す。
4. メモリ時間上位のFunctionで、長時間の外部API待機と大容量ファイル処理を見直す。
5. 70%を超えた状態が2か月続く場合は、利用者数と機能要件からプランを再評価する。

## 100%到達時

- 使用済みのActive CPUはコード修正では元に戻らない。次の利用枠更新までは、本番のβテスト利用ログを `summary` または `off` で運用する。
- まず `/api/beta/events` の呼び出し集中、エラーの再試行、短時間ポーリングを確認する。
- Hobbyではルート別Active CPUメトリクスのCLI照会にObservability Plusが必要なため、実行ログとコード上の呼び出し頻度を併用して調査する。

## 注意

アクセス数やデータ量に上限を設けない限り、無料枠内を絶対に保証することはできない。上記は通常利用時の消費を抑え、超過前に検知して対応するための設計である。
