# Classbase バックアップ・復旧ランブック

最終更新: 2026-10-03

## 目標

- RPO（許容データ損失）: 通常時24時間以内。重大な一括更新前は直前バックアップを追加する。
- RTO（復旧目標）: 4時間以内に代替運用を開始し、8時間以内に復元先で主要データを検証する。
- Firestore: 日次バックアップを14週間保持し、PITRも有効化する。
- Storage: ソフトデリートを最低7日保持する。重要な提出画像・教材は削除前に世代または別保管を確認する。

Firestoreのスケジュールバックアップは新しいデータベースへ復元する。既存本番データベースを削除する「同名復元」は、元データを恒久的に失うため、経営責任者・業務責任者・技術責任者の3者承認なしに実施しない。

## 定期確認

毎週、次を実行する。

```bash
npm run ops:backup:audit
```

出力に `problems` が1件でもあればP1運用課題として当日中に対応する。`warnings` は3営業日以内に判断する。秘密値、アクセストークン、サービスアカウント鍵を結果へ保存しない。

毎月、Google Cloud Consoleで以下を確認する。

1. Firestoreの最新日次バックアップが24時間以内に成功している。
2. 最古バックアップが保持方針どおり残っている。
3. Storageのソフトデリート保持期間が7日以上である。
4. Firebase Authenticationの利用者一覧を、アクセス制限された管理領域へ暗号化してエクスポートする。
5. Vercel環境変数の変数名一覧と設定責任者を台帳で確認する。値をリポジトリや通常の共有ドライブへ保存しない。

## Firestore復元演習

四半期ごとに、本番とは別の新規データベースIDへ復元する。

1. 最新の正常なバックアップと復元対象時刻を記録する。
2. 新規データベースIDを `restore-drill-YYYYMMDD` とする。
3. Cloud Consoleが提示する復元コマンドを二人で照合して実行する。本番の `(default)` を宛先にしない。
4. 復元完了後、次の代表コレクションの件数とサンプルを原本と突合する。
   - `users`
   - `course_registrations`
   - `shift_assignments`
   - `attendance`
   - `work_records`
   - `attendance_details`
   - `homework_assignments`
   - `submissions`
   - `notifications`
5. 親子紐付け、講座登録、授業配置、勤怠実績と明細、提出画像パスを最低各3件確認する。
6. 復元先をアプリ本番へ接続しない。演習結果を記録後、承認を得て復元先を削除する。

## Storage復旧演習

四半期ごとに検証用ファイルをアップロードし、削除後にソフトデリートから復元する。本物の提出画像・教材を削除試験に使わない。

1. 専用接頭辞 `drill/restore-test/` に検証ファイルを作る。
2. generation、ハッシュ値、Content-Typeを記録して削除する。
3. Cloud Consoleまたは `gcloud storage restore` で復元する。
4. 復元後のハッシュ値、Content-Type、ダウンロード権限を照合する。
5. 検証ファイルだけを削除し、演習記録へ承認者を残す。

## 本番障害時の復元判断

1. 書込みを止めるか対象機能を停止し、障害開始時刻を確定する。
2. 誤削除、誤更新、漏えい、アプリ不具合、外部障害を切り分ける。
3. バックアップ時刻以降の正常更新件数を算出し、失われるデータを一覧化する。
4. まず新規データベースへ復元し、代表件数と関係整合性を確認する。
5. 部分復旧が可能なら必要文書だけを監査付き移送する。全面切替や同名復元は3者承認を必須とする。
6. 復旧後、重複ID、孤立参照、勤怠金額、講座登録、通知再送の有無を確認する。
