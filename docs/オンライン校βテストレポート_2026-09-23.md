# オンライン校βテスト利用状況レポート

集計期間：2026年9月7日〜9月23日（JST）  
集計対象：9月23日時点で有効なオンライン校の生徒アカウント

## 1. 結論

対象58人のうち42人（72.4%）でログインを確認し、26人（44.8%）がClassBase経由で授業に参加した。ログイン済みの生徒に限ると、授業参加率は61.9%である。18人は異なる2日以上で授業参加が確認でき、ログイン後の利用は一定程度進んでいる。

一方、開始3日以内にログインが確認できたのは23人で、ログイン確認者42人のうち19人（45.2%）は開始4日目以降だった。9月23日時点でも16人は未ログインである。今回「かなりログインを促したが時間がかかった」という運用実態と合わせると、本導入の最大リスクは、授業機能よりも初回ログインまでの手間と校舎のサポート負荷である。

## 2. 主要指標

| 指標 | 人数 | 対象58人に対する割合 |
|---|---:|---:|
| 現在有効なアカウント | 58 | 100.0% |
| ログイン確認 | 42 | 72.4% |
| 未ログイン | 16 | 27.6% |
| ClassBase経由の授業参加 | 26 | 44.8% |

利用段階ごとの転換率は、有効アカウントからログイン確認までが72.4%、ログイン確認から授業参加までが61.9%、授業参加から複数日参加までが69.2%だった。最も大きな離脱は、アカウントが用意されてから最初にログインするまでに発生している。

## 4. 本導入時の移行方針

本導入では、IDと初期パスワードの再入力を生徒に求める方式を避け、旧システムにログイン済みの状態から新システムへ一度の操作で移行できる「認証ブリッジ」を推奨する。

1. **事前照合**：旧システムの生徒番号と新システムのUIDを運営側で対応付け、重複、退会者、学年、所属校の不一致を先に解消する。
2. **ワンクリック移行**：旧システムの「新システムを開く」から、短時間・1回限りの署名付きトークンを発行する。新システムでFirebaseのカスタムトークンへ交換し、新たなID・パスワード入力なしで本人として開始させる。
3. **初回画面を最小化**：氏名、学年、所属だけを確認し、授業参加画面まで直接案内する。メール認証は生徒の利用開始条件にしない。
4. **例外対応**：旧システムに入れない生徒だけ、期限付きQRコードまたは1回限りのコードで有効化する。共通初期パスワードは使用しない。
5. **2〜3週間の併走**：「未発行／移行リンク発行済み／交換成功／ホーム表示／参加ボタン表示／授業参加」の段階別一覧で未移行者を支援する。

### セキュリティ要件

- 移行トークンは短時間・1回限り、サーバー間署名、再利用拒否、監査ログ付きとする。
- 生徒番号だけで本人確認を完了させない。
- 対応表の不一致は自動で別人に結び付けず、例外確認へ送る。
- 発行・交換のレート制限、失効、問い合わせ時の本人確認手順を定める。

## 5. 本番移行時に計測する項目

- アカウント対応付け完了
- 移行リンク発行
- 認証トークン交換成功・失敗理由
- 初回ホーム表示
- 参加ボタン表示・クリック
- Zoom起動成功
- 例外導線の利用
- 1人を有効化するまでの案内回数と対応時間

## 6. 集計条件と制約

- 生徒ロール、校舎コード112または校舎名がオンライン校で、退会・アーカイブ・無効等ではないアカウントを対象とした。対象者のAuth欠損、Auth無効、学年欠損はすべて0件だった。
- ログインは、期間内の認証済み画面イベントを主な根拠とした。ログイン確認者42人全員で該当イベントがある。
- 授業参加はClassBaseの参加ボタンまたは本人操作の参加記録で把握した。旧システムやZoomの直接URLから参加した場合は含まれない。そのため44.8%は全授業の実出席率ではなく、ClassBase経由参加率である。
- 今回のデータだけでは、遅れてログインした直接原因が案内不足、認証失敗、端末事情のどれかは特定できない。「繰り返し促した」という評価は運用担当者から提供された状況説明であり、イベントログから因果を証明したものではない。
